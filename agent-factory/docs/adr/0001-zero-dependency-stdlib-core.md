# ADR-0001: Zero third-party dependencies in the runtime core

**Status:** Accepted · **Date:** 2026-09-01

## Context
The v0.4 runtime needs a queue, a store, schema validation, and an async
execution model. The obvious path is Pydantic + SQLAlchemy + Celery/Arq + Redis.

The target environment had **no third-party packages installed**, and the mandate
requires a benchmark suite that is actually run, not described.

## Decision
The runtime core (`af/`) depends only on the Python 3.11 standard library.
Third-party libraries are permitted only in *adapters* (a real model provider, a
PostgreSQL driver) behind an existing port.

Consequences of that: a hand-written JSON Schema subset (`af/jsonschema.py`),
dataclasses instead of Pydantic, and hand-written SQL instead of an ORM.

## Rationale
- A benchmark that cannot run is worth less than a slow one that can. Zero
  dependencies means the suite runs on any machine with Python 3.11.
- The pieces we would import are the pieces we most need to control. Queue
  semantics (leases, DLQ, idempotency) and validation are *where the governance
  lives*; delegating them to a library would mean auditing the library's
  semantics rather than owning them.
- Hand-written SQL keeps the PostgreSQL migration legible: every statement is
  visible and portable, rather than generated by an ORM whose dialect behaviour
  must then be re-verified.

## Costs — accepted, not hand-waved
- `af/jsonschema.py` implements a **subset**: no `$ref`, no `allOf`/`anyOf`/
  `oneOf`, no format assertions. Contracts needing those must wait for a real
  validator to be swapped in.
- No connection pooling, migrations tooling, or admin UI comes for free.
- More code to own: ~4,600 lines that a dependency-heavy build would not have.

## Revisit when
The runtime moves to PostgreSQL (ADR-0002). At that point a driver is required
anyway, and `jsonschema` and a migration tool should be adopted at the same time.
